# 검사 규칙

## 한 줄 요약
**"캡처는 검사다, 증거가 아니다."** 찍는 목적은 "했다"를 남기는 게 아니라 **틀린 걸 찾는 것.** 찾으면 그 바퀴 안에서 고치고 다시 찍는다.

## 검사 3층 (아래부터 순서대로, 아래가 실패하면 위로 안 올라감)
| 층 | 무엇 | 도구 | 실패하면 |
|---|---|---|---|
| 1. 기계 검사 | 컴파일, 이름·폴더 규칙, 자리표시, 중복 ID | 콘솔, `tools/check_conventions.py`, EditMode 테스트 | 커밋 금지 |
| 2. 동작 검사 | 실제로 눌러서 돌아가나 | PlayMode 테스트, **실제 입력 경로 주입** | 커밋은 가능, 같은 바퀴에 fix |
| 3. 눈 검사 | 화면이 이상하지 않나, 플레이어가 쓸 수 있나 | 캡처를 **열어서** 체크리스트 + 플레이어 눈 다섯 칸 (`PlayerEye.md`) | 같은 바퀴에 fix, 못 고치면 INBOX `막힘` |

엔진별 구체 방법은 `docs/checks/<엔진>.md` — Unity `docs/checks/unity.md`, Unreal `docs/checks/unreal.md`, Godot `docs/checks/godot.md`.

## 규칙
1. **못 한 검사는 "통과"가 아니라 "못 함"으로 적는다. "통과"는 실제로 명령을 돌리고 그 출력의 마지막 줄을 STATUS 에 인용했을 때만 쓴다.** `검사: 1층 통과(\`✔ 규칙 검사 통과 (경고 0 / 미정 숫자 0)\`) / 2층 통과(\`Passed: 3, Failed: 0\`) / 3층 못 함(에디터 꺼짐)`. 인용 없는 "통과"는 감독이 `결함`으로 되돌린다. 왜: 실행하지 않고 "통과"라고 쓴 바퀴가 여러 프로젝트에서 반복됐고, 거짓 통과 한 번이 이후 모든 바퀴를 속인다.
   - **판단은 이름·문자열 패턴이 아니라 실제 결과로.** 종료 코드·결과 파일(`logs/editmode.xml` 등)·`stat` 시각으로 "이번 실행의 결과"인지 확인한다. 결과 파일은 고정 경로에 쓰고, 옛 파일이 남아 있으면 먼저 지운다. `cp`/`mv` 는 `|| exit 1`.
   - 역검증(일부러 깨서 실패가 나는지)은 **파일을 옮기거나 이름을 바꾸지 않고** 테스트 값·별도 사본으로 한다. 왜: `mv` 가 mtime 을 건드려 빌드 캐시가 오염된다.
   - **3층(눈 검사)의 "통과"는 캡처를 실제로 열어 봤을 때만이다.** 캡처 파일을 Read 로 열고(또는 캡처 도구가 그림을 돌려주고), 아래 체크리스트를 항목별 예/아니오로 본 뒤 `3층 통과(레퍼런스 대조: docs/reference/<대상>.md, captures/<파일>.png)` 처럼 **어느 그림을 봤는지** 적는다. `loop.sh` 가 바퀴 끝에 그 바퀴의 도구 기록을 보고, 그림을 하나도 안 열었는데 "3층 통과" 라 적혀 있으면 `alerts.log` 에 올린다. **눈으로 본 판정은 Jev 에 묻지 않는다** — Jev 는 명령 출력 글을 판정하는 도구라 그림 판정에는 늘 "근거 부족"을 낸다. 왜: 캡처를 찍고 눈으로 대조까지 했는데 판정기가 인정을 안 해서 "못 함"으로 적은 바퀴가 쌓였고, 그 사이 눈 검사가 사실상 사라졌다 (한 프로젝트의 최근 100바퀴 중 3층 통과는 7번).
   - **1·2층 인용은 STATUS 에 적기 전에 제3 판정기 Jev 에 묻는다.** `python3 tools/jev.py evidence "<어떤 검사인지 적은 주장>" "<인용한 출력>"` → `SUPPORTED` 일 때만 "통과". `NOT_SUPPORTED` 면 통과라 쓰지 않는다(다시 돌리거나 "실패"). `UNAVAILABLE`(키·네트워크) 이면 `통과(jev 미확인)` 로 적는다 — 이때도 인용은 실제 출력 그대로여야 한다: `loop.sh` 가 바퀴 끝에 `loop/lap_audit.py check` 로 STATUS 의 모든 `통과(\`인용\`)` 을 그 바퀴의 도구 출력 기록(`logs/lap-<n>.jsonl`)과 대조하고, 없으면 `alerts.log` 에 "검사 인용 불일치"를 올린다. Jev 가 없어도 지어낸 인용은 걸린다. 주장은 `1층 기계 검사(check_conventions.py) 통과` 처럼 **무엇을 돌렸는지** 넣는다 — 맨 "1층 통과" 는 Jev 도 못 믿는다. **역검증**(일부러 깨서 검사가 잡는지 확인)의 인용은 세 번째 인자 `fail` 로 묻는다: `python3 tools/jev.py evidence "역검증: <무엇을 깨자 무엇이 잡혔나>" "<실패 출력>" fail` — 기본(`pass`)은 "통과했다"는 주장만 판정하므로 실패 출력을 붙이면 구조적으로 NOT_SUPPORTED 가 나온다. 왜: 자기 결과를 자기가 채점하면 후하다. Jev(TypeSafe System One)는 글을 쓰지 않고 판정만 돌려주는 모델이라 변명을 못 만든다.
2. **UI 는 코드 호출이 아니라 실제 입력으로 검사.** `button.onClick.Invoke()` X → 포인터 이벤트 주입/Input System 테스트로 클릭. 왜: 코드로 부르면 버튼이 다른 창에 가려져 있어도 통과한다.
3. **자리표시 검출은 눈이 아니라 코드로.** `-1`, `TBD`, `Lorem`, `New Text`, 분홍색(누락 셰이더), 흰 네모(누락 스프라이트)는 검사기가 찾는다.
4. **같은 지적 두 번 → 규칙으로 올리고 → 검사로 만든다.** 순서: `docs/postmortems/` 에 기록 → 해당 컨벤션 문서에 규칙 추가 → `check_conventions.py` 나 테스트에 검사 추가. 왜: 규칙만 쓰면 다음 AI가 또 어긴다. 검사는 못 어긴다.
5. 사람이 Play 중이거나 실기 테스트 중이면 루프는 코드·에셋 변경 금지 (INBOX 맨 위 `보류:`).
6. **테스트는 밸런스 숫자에 기대지 않는다.** 테스트 안에서 **테스트 전용 값**을 넣은 데이터를 만들어 쓴다 (Unity `ScriptableObject.CreateInstance`, Unreal `NewObject<UDataAsset>`, Godot `.new()`). 왜: DESIGN §6 숫자가 바뀔 때마다 테스트가 깨지면 안 된다.
7. 런타임 코드는 `-1` 을 만나면 에러 로그(`[Data] 미정 숫자: <에셋>.<필드>` — Unity `Debug.LogError`, Unreal `UE_LOG(..., Error, ...)`, Godot `push_error`)를 찍고 안전한 동작(이동 0, 무적 등)을 한다. 왜: 안 채운 숫자가 조용히 이상한 게임을 만들지 않게.
8. **보이는 것(UI·캐릭터·아이템)의 3층은 레퍼런스 시트와 나란히 대조**한다 (`Reference.md` §4). 시트가 없으면 `못 함(시트 없음)`. 자리표시 품질(네모·단색·기본 스킨)은 3층 실패다.
9. **엔진 로그의 `Error:` 줄은 눈으로 넘기지 않는다.** 줄마다 `python3 tools/jev.py noise <엔진> "<줄>"` → `NEEDS_REVIEW` 는 그 바퀴에서 원인을 보고 STATUS 에 적는다. `KNOWN_NOISE` 는 STATUS 에 줄 수만 적는다. 왜: "늘 나오는 에러"라며 진짜 에러를 같이 묻어 버린 일이 있었다.
10. **결함 지적(감독·리뷰)은 `python3 tools/jev.py verdict "<지적 + 근거>"` 로 판정한 뒤 올린다.** `CONFIRMED` 만 INBOX `결함`, `PLAUSIBLE` 은 `확인`, `NOT_REAL` 은 버린다. 왜: 근거 없는 결함이 INBOX 맨 위에 오면 루프가 헛바퀴를 돈다. **사람이 직접 한 지적은 판정하지 않고 그대로 `결함` 이다** — 사람 눈이 최종 기준이다.
11. **플레이어가 보거나 만지는 조각은 "플레이어 눈" 다섯 칸을 같이 본다** (`PlayerEye.md`): 처음 하는 사람 · 목표 기기의 손 · 게임 카메라에서 보이나 · 장르 상식 · 갇힘 없음. STATUS 검사 칸 뒤에 `플레이어 눈:` 한 줄. 왜: 사람이 "이상하다"고 한 것들은 거의 전부 1·2층이 통과한 조각이었다. 시험은 부품을 보고, 플레이어는 화면과 손을 겪는다.
12. **보이는 동작(손·도구·자세)을 숫자로만 확인한 줄은 표에 "캡처 안 봄"이라고 적는다.** 합격은 게임 화면 캡처를 직접 열어 보고 레퍼런스 프레임과 나란히 비교한 뒤에만. (사람 지시 2026-10-06)
13. **캡처는 한 번 찍고 끝낸다.** 구도·조명·배치를 다듬으려 다시 찍지 않는다. 대상이 가려지면 그 사실을 STATUS 에 한 줄 적고 넘어간다. 다시 찍기는 대상이 화면에 아예 없을 때 최대 1회. 크기·시간·거리 판정은 캡처 픽셀이 아니라 로그 숫자로. 캡처용 새 검사 스위치는 기존 것으로 안 될 때만. 왜: 사람 지시(2026-09-23, 루프#160 이 한 장에 여러 번 재촬영).
14. **오류·경고는 넘기지 않는다.** 컴파일·테스트·검사기 오류·경고는 원인을 로그로 확인해 고친 뒤 다시 돌려 통과를 확인한다. 못 고치면 STATUS 에 "실패"+원인+로그 경로, INBOX `막힘`. 같은 오류가 두 번이면 STATUS "같은 실수 방지" 줄에 원인·예방책. 왜: 사람 지시(2026-09-18).

## 캡처 눈 검사 체크리스트 (3층)
- [ ] 분홍색 / 검정 네모 / 흰 네모 없음 (누락 재질·스프라이트)
- [ ] 글자 잘림·겹침 없음, 한글 깨짐(□□) 없음
- [ ] 자리표시 글자 없음 (`New Text`, `TBD`, 키 이름 그대로 `ui.btn.ok`)
- [ ] 캐릭터 발이 땅에 붙어 있음, 정렬 순서(앞뒤) 맞음
- [ ] 픽셀아트면 흐림(필터링) 없음, 크기 배율이 정수
- [ ] 이번 조각의 합격 기준 문장이 화면에서 보임
- [ ] **실제 플레이 시점(게임 카메라)** 캡처다 — 에셋 미리 보기·에디터 뷰포트가 아님
- [ ] 손에 든 것·캐릭터 얼굴·이번 조각의 주인공이 그 캡처에서 보이고, 크기가 시트의 비율 숫자 안 (`PlayerEye.md` ③)
- [ ] 레퍼런스 시트 대조 6항목 통과 (`Reference.md` §4) — 어느 시트인지 STATUS 에 적음
- 캡처 파일: `captures/<바퀴번호>_<범위>_<설명>.png` — 합격 캡처만 커밋, 나머지는 `captures/tmp/`
