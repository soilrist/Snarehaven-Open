# 브랜치 전략

## 한 줄 요약
**`main` = 사람이 확인한 것만. `develop` = 루프가 일하는 곳.**
비유: `develop` 은 주방, `main` 은 손님 식탁. 요리사(루프)는 주방에서만 일하고, 맛본 사람(감독+사람)이 식탁에 올린다.

```
main      ●───────────●───────────●        ← 태그 v0.1.0, v0.2.0 …
           \         /           /
develop     ●─●─●─●─●─●─●─●─●─●─●          ← 루프 커밋 (바퀴마다)
                 \     /
feature/x         ●─●─●                     ← 크거나 위험한 작업만
```

## 브랜치 종류
| 브랜치 | 누가 | 규칙 |
|---|---|---|
| `main` | 사람(감독 제안) | 직접 커밋 금지. `develop` 을 합쳐서만 바뀜. 합칠 때 태그 |
| `develop` | 루프 일꾼 | 평소 모든 바퀴는 여기 커밋 |
| `feature/<범위>-<짧은이름>` | 사람·감독만 | 사람이 직접 하는 큰 작업. **루프는 쓰지 않는다** |
| `fix/<범위>-<짧은이름>` | 사람·감독만 | `main` 에서 급한 버그 |
| `exp/<이름>` | 누구나 | 실험. 합치지 않는 게 기본 |

이름은 소문자·하이픈: `feature/combat-resonance`, `fix/ui-tooltip-stuck`.

## 규칙
1. **루프는 `develop` 에서만 일한다.** 브랜치를 만들거나 바꾸지 않는다. `loop.sh` 가 바퀴 시작 전에 확인하고, 아니면 멈추고 `logs/alerts.log` 에 `막힘`. 왜: 잘못된 브랜치에 몇십 바퀴 쌓이는 사고 방지. 켤 때는 `loop/ctl.sh on` 이 작업 트리가 깨끗하면 `develop` 로 옮겨 주고, 없으면 지금 브랜치에서 만들어 준다 (감독이 손으로 브랜치를 만들 필요 없음).
2. **`feature/`·`fix/` 는 사람·감독이 루프를 멈춘 상태에서만** 쓴다. 끝나면 `develop` 에 `git merge --no-ff -m "merge: feature/combat-resonance → develop"` 로 합치고 브랜치 삭제.
3. **`main` 으로 합치기 조건** (감독이 확인, 사람이 승인):
   - 컴파일 에러 0, 테스트 전부 통과, `check_conventions.py` 통과
   - INBOX 에 열린 `결함`·`막힘` 없음
   - 사람이 실제로 한 번 플레이해 봄
   - `CHANGELOG.md` 갱신 + 버전 태그 (Versioning.md)
   - **루프를 `wrapup` 으로 멈추고 실행 중인 바퀴가 없을 때** 합친다 (같은 폴더라 브랜치를 바꾸면 루프가 멈춤). 합친 뒤 반드시 `develop` 으로 돌아온다.
   - 합치기 메시지: `merge: develop → main (v0.1.0)`
4. **강제 푸시(`--force`) 금지.** 되돌릴 땐 `git revert`.
5. 사람이 에디터로 작업 중이면 루프는 **같은 파일을 건드리지 않는다** — INBOX 맨 위에 `보류:` 가 있으면 그 범위는 손대지 않음.

## 합치기 충돌이 나면
씬·에셋 충돌 해결법은 엔진마다 다르다 (Unity YAML → `UnityYAMLMerge`, Unreal 바이너리 `.uasset`/`.umap` → 병합 불가·`--ours`/`--theirs` 선택, Godot 텍스트 `.tscn`/`.tres` → git 기본 병합 대체로 동작) → **`docs/engines/<엔진>.md`** "브랜치 합치기 충돌" 절. 안 되면 INBOX `막힘:` 로 사람에게. AI가 씬·에셋을 손으로 고치지 않는다.
